# ShortForge 개발 하네스

## 실행 모드: 서브에이전트 위임

분석·검토·검증·배포는 서로 대화할 필요가 없고 결과만 받으면 된다. 그래서 단계마다 `Agent`를 한 번 부르고(`name` 없이, 기본 백그라운드), 결과를 메인이 모아 사용자에게 보고한다. **구현은 메인이 직접 한다**: 맥락이 크고 사용자와 주고받으며 고치는 일이라 떼어 내면 손해다.

| 에이전트 | `subagent_type` | 맡는 일 | 산출물 |
| --- | --- | --- | --- |
| 분석 | `sf-analyst` | 근거 있는 개선점 우선순위표 | `_workspace/01_analyst_findings.md` |
| 검증 | `sf-verifier` | 데이터 사본으로 실제 실행·캡처·정리 | `_workspace/02_verifier_report.md` |
| 검토 | `sf-reviewer` | 커밋 전 변경을 프로젝트 규칙으로 검토 | `_workspace/03_reviewer_findings.md` |
| 배포 | `sf-releaser` | 사전 배포판 점검표 실행 | `_workspace/04_releaser_log.md` |

`_workspace/`는 저장소 루트에 두고 git에서 뺀다(`.gitignore`). 사후 확인을 위해 지우지 않는다.

## 작업 절차

### 0단계: 요청 종류와 이전 결과 확인
- "개선점 확인/도출/점검" → 1단계만 하고 표를 보여 준 뒤 멈춘다(사용자가 고른다).
- "진행"(앞서 제안한 표가 있음) → 추천 순서의 항목으로 2~5단계. 삭제·유료 설정·키 발급처럼 사람이 정할 항목은 건너뛰고 그렇다고 알린다.
- "배포" → 6단계만.
- "다시/이어서/그 부분만" → `_workspace/`의 해당 파일을 읽고 그 단계만 다시 한다. 새 주제의 요청이면 기존 `_workspace/`를 `_workspace_{YYYYMMDD-HHMM}/`로 옮기고 시작한다.

### 1단계: 개선점 찾기 — `sf-analyst`
프롬프트에 범위, 사용자가 이미 거절·보류한 항목, 최근에 끝낸 일을 적는다. 결과 표를 사용자 언어로 다듬어 보여 준다(근거 수치 유지).

### 2단계: 구현 — 메인
- **화면 구조가 크게 바뀌면 시안부터**: 단계 수·첫 화면·주요 흐름이 바뀌는 개편은 구현 전에 화면 시안(배치 그림과 흐름)을 보여 주고 확인받는다. 내부 단계(Project JSON 계약)는 유지하고 화면에서 묶는 방식을 먼저 검토한다. 판단 기준은 `sf-review-rules` 7절(초보자 기준)이다.
- 루트 `CLAUDE.md`의 규칙을 따른다. 여러 줄 편집은 Edit 도구를 우선하고, 파이썬 스크립트로 고쳤으면 역슬래시·줄바꿈이 맞는지 결과 파일을 다시 읽어 확인한다(실제로 여러 번 깨졌다).
- 백엔드: `uv run ruff check --fix . && uv run ruff format .` 뒤 관련 테스트, 마지막에 전체 `uv run pytest -q`.
- 프론트: `npx tsc --noEmit && npm run lint`. 화면 흐름을 바꿨으면 `frontend/e2e/`도 맞춘다. prettier는 내가 고친 줄만 바뀌는 파일에만 쓴다.

### 3단계: 실제 검증 — `sf-verifier`
자동 테스트가 못 보는 것(실제 렌더, 실제 무료 API, 화면)이 바뀌었을 때만 부른다. 화면을 바꿨으면 '초보자 흐름 걷기'를 확인 항목에 넣는다. 프롬프트에 확인 항목과 비교할 이전 수치를 적는다. 결과에 "확인 못 함"이 있으면 그대로 보고한다(우회하지 않는다).

### 4단계: 규칙 검토 — `sf-reviewer`
커밋 전에 부른다. `[치명]`이 있으면 고친 뒤 다시 부른다. `[수정]`은 고치거나, 고치지 않으면 이유를 보고에 적는다.

### 5단계: 문서·커밋·CI — 메인
- `CHANGELOG.md` "다음 버전", 구조가 바뀌면 `CLAUDE.md`, 실측·결정은 `docs/DECISIONS.md`.
- 스테이징 확인 후 커밋·푸시하고 CI가 `completed success`인지 본다(백엔드 + 화면 테스트).
- 보고: 무엇을 했는지, 실측 결과, 확인 못 한 것, 남은 일. 배포는 사용자가 요청할 때만.

### 6단계: 배포 — `sf-releaser`
프롬프트에 새 태그(마지막 태그 + 1), 날짜, 제목, 소개 페이지 연혁 한 줄을 넣는다. 결과의 배포판 주소와 테스트·CI 결과를 보고한다.

## 데이터 전달
- 에이전트 → 메인: 반환 메시지 + `_workspace/{번호}_{에이전트}_{산출물}.md`
- 메인 → 에이전트: 프롬프트에 범위·항목·이전 파일 경로를 적는다. 에이전트는 대화 맥락을 모르므로 필요한 사실(예: "유료 모드는 .env에서 켜져 있음", "검증할 프로젝트 ID")을 빠짐없이 넣는다.

## 오류 처리
- 에이전트가 실패하면 한 번 다시 부른다. 또 실패하면 그 단계 없이 진행하고 보고에 누락을 적는다.
- 사용량 한도·인증 만료·권한 거부는 다시 시도하지 않는다. 남은 산출물을 직접 열어 어디까지 됐는지 확인하고, 사용자에게 알린다(한도면 풀리는 시각도).
- 에이전트 대신 빈칸을 채울 때는 직접 확인한 사실만 쓴다. 에이전트의 판단을 추측해 적지 않는다.
- 검증이 서버를 남겼을 수 있으면 `python .claude/skills/sf-verify/scripts/verify_env.py cleanup`을 메인이 한 번 더 실행한다.

## 테스트 시나리오

### 정상 흐름
"다음 개선점 확인해 줘" → 0단계: 확인 요청 → 1단계 `sf-analyst` → 표 보고 후 멈춤. 이어서 "진행" → 2단계 구현 → 3단계 `sf-verifier`(렌더가 바뀐 경우) → 4단계 `sf-reviewer` 발견 없음 → 5단계 커밋·CI 통과 보고. "배포" → 6단계 `sf-releaser` → 배포판 주소 보고.

### 오류 흐름
3단계에서 외부 사이트가 403으로 막음 → 검증 보고서에 "확인 못 함 — 403" → 메인은 우회하지 않고 그 항목을 미확인으로 보고, 나머지 항목만 근거로 진행. 6단계에서 새 clone 테스트 실패 → `sf-releaser`가 태그 없이 멈춤 → 메인이 원인을 고치고 커밋 → `sf-releaser`를 다시 불러 3단계부터 이어서.
